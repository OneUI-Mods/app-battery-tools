# 0.3.0の検証

## 自動・仮想端末

- JVMテスト68件成功。既存49件に加え、所有者・リソースの同一性、引き継ぎ済み資源の保持、同時購読による採用、最後の失敗後の解放、別所有者との分離、解放失敗の分離、二重解放の防止、取得した参照分だけの返却、正常開始・管理マップ登録済みの場合の保持、設定フラグ・状態項目と解析結果のキー衝突の拒否を確認。
- Android 16／17のエミュレーターで、従来3対象と新規4対象の実APKに対するDexKit照合が成功。
- 新規4対象では、取得したメソッド・フィールドを同じAPKのクラスローダーへ解決できることを確認。R8でObjectフィールドへまとめられたSmartThingsの所有者候補と、具体的なFlowableエミッター実装の照合も含む。
- ウェザーニュースの実APKにある停止メソッドを、未接続でonCreateを呼ばないApplication実体に対して実行。元の停止後はTimerへ予約を追加できる（取り消されていない）ことを再現。製品と同じOwnedTimerCleanupを先に通すと、Timerが取り消され、元のメソッドがフィールドをnullへ戻すことを確認。実際のBLE探索、天気通知、アカウント初期化は実行していない。
- Android 16／17で10対象を含む設定画面を表示し、最後のSimeji設定までスクロールできることを確認。Android 17ではダークモード・文字150%も確認。
- Simejiの個別スイッチOFFがProviderへ反映され、設定アプリのプロセス再起動後も保存され、ONへ戻せることをエミュレーターで確認。試験後はONへ復元。
- 既存のWindows SDK受け渡しとEQ出力先IDの検証も引き続き成功。

## 実機・効果の範囲

実機でのフック初期化の確認と、機器追加・Matter探索・センサー設定変更・長期の電池削減量の検証を分けて扱う。機器操作と電池削減量の実証は未実施。仮想端末のAPK照合・所有関係テストを、全機器との互換性の証明とは扱わない。

実機への初回読み込みで、ウェザーニュースの設定キーとタイマーフィールドの解析キーが同名だと、Boolean設定を文字列で上書きしてOFF扱いになることを検出した。解析側のキーを分離し、解析ルールの世代も更新した。Providerは今後も設定・状態の予約キーとの衝突を拒否し、この制約を全APK照合でも検証する。

Simejiは診断用ANR監視の登録を止める機能であり、そのSDKによる新しいANRレポートは取得できなくなる。Android本体の異常処理や文字入力の機能は対象外。対象SDKがもともと有効でなければ、このスイッチだけによる削減効果は出ない。

ウェザーニュースは設定変更でTimerへの参照を失う前に適用する補正。すでに漏れて参照を失ったタイマーの回収機能ではない。再起動後の設定変更から作用する。

常駐サービス・定期ジョブ・新しいポーリングは追加していない。全対象の設定・解析キャッシュは引き続きこのモジュール自身の内部データだけに保存する。


## 実機への反映と起動確認

署名済みrelease版を導入し、新規4対象の解析ready・フックactive・診断エラーなしを確認した。背景でのApplication初期化で確認し、機器制御はしていない。端末のboot ID、system_server、SystemUI、ホームのPIDとSELinuxは維持されている。

続いてユーザーがGoveeの起動クラッシュを報告した。終了記録はSIGSEGV、0xdead5020への分岐で、モジュールの初期化完了前に落ちていた。Goveeだけスコープを外して起動を確認し、起動の後へ準備を送る版を比較したところ、スコープとWi-Fi連動をONにしたまま同一PIDで約73秒以上の生存・wifi_active・エラーなしを確認した。スコープ除外には戻していない。保護コードへのパッチ・アプリの再署名・データ削除・ログイン変更はしていない。

デバイス一覧が空だった件は、ユーザーによりログアウト状態だったと確認された。起動クラッシュやBLE補正の結果と混同しない。Goveeの起動・フック初期化ができたことと、起動前からの全スキャンやWi-Fi切断時の振る舞いまで実証したことも分ける。
