# Windowsにリンク：通信資源の残留を調査

## 対象と現在の判断

- パッケージ: `com.microsoft.appmanager`
- 調査版: 1.26101.106.0
- APK SHA-256: `f030033c9db16a92ebf58cf86047dfdb348db959c545bba72e726495273591d8`
- 調査段階: 電池記録、2回のスレッド統計、FDの種別、APKのAgentServiceとBeaconLocationControllerを確認。
- 判断: 次点。多い資源数を確認したが、接続資源の漏れや大きな削減余地はまだ証明していない。フック対象へ即採用しない。

## 実機の観測

- 約14時間の電池統計で、主プロセスはユーザーCPU約5分24秒、カーネルCPU約16分57秒。
- 消灯中の割当推定はCPU約10.0mAh、Wi-Fi約0.206mAh。Digi Policeの位置要求ほど明確に大きい対象とは現時点で言えない。
- 実機の主プロセスに317スレッド。約104秒後も同数だった。
- 主な同名スレッドは `udp(asio)` 75本、`pDCT IO thread` 59本、`libbasix-thread` 51本、`ICE Agent` 14本。
- 同期間に既存スレッド合計でCPU約3.27秒を使用した。1コア換算で約3.15%だが、画面OFFの定常試験ではなく、端末を利用している間の観測。
- FDはソケット105、anon_inode 294、通常ファイル279、pipe 2。
- RSSは約118MiB。大きなVmSizeやスレッド数を、そのまま実メモリ消費・電池消費と見なさない。

## APKの確認

`com.microsoft.mmx.agents.AgentService.onDestroy()` には、LocaleChange購読のキャンセル、ハンドラ停止、使用量記録の停止、Mediatorバインド解除がある。Digi Policeと同じように「終了処理がない」とは言えない。

常駐エージェント、写真・通知・ファイル・画面共有・接続状態の管理が分かれている。確認したBeaconLocationControllerはインターフェースであり、実装のタイマー等の問題はまだ特定していない。

## 改善候補と必要条件

古い接続試行ごとのUDP／ICE／pDCT資源が切断後に残っているなら、現在の接続を保ったまま古い資源だけを終了できる可能性がある。ただし資源の所有者、接続数との関係、SDKが意図したプールかを確認するまでは仮説。

次に調べるのは、接続・切断の世代ごとの生成／解放、通信断からの再接続での増加、切断済みオブジェクトとスレッドの対応。現在317本から増えなかったという観測は、漏れの証拠にはならない。

通知同期・ファイル転送・即時接続・画面共有を止めたり、全SDKスレッドを強制終了する案は採用しない。Java側でライフサイクルを扱える箇所が特定できた場合だけ、DexKitの型・呼び出し・一意性を検証してアプリ別スイッチへ追加する。

## 未検証

画面OFFで条件を揃えた比較、再接続に伴う単調な増加、ネイティブSDKの所有関係、改善後の機能・消費比較は未実施。
